# Spendprint 설계서

- 날짜: 2026-11-23
- 상태: 승인됨(2026-11-23). 사용자가 "보정 범위"(§7) 추가를 조건으로 승인했다
- 이 문서에는 실제 금융 데이터(금액, 이름, 가맹점)를 적지 않는다. 구조와 규칙만 적는다.

## 1. 의도

Spendprint는 한 사람이 자기 PC에서 쓰는 개인 지출 분석 사이트다. 뱅크샐러드 앱에서 내보낸 엑셀 파일을 올리면, 소비·지출 패턴·월 고정비·수입·자산을 토스풍 화면으로 정리해 보여준다.

만드는 이유:

- 여러 카드와 계좌에 흩어진 돈의 흐름을 한 곳에서, 믿을 수 있는 숫자로 보고 싶다.
- 뱅크샐러드의 분류는 그대로 믿을 수 없다. 실제 파일에서 급여가 이체로 잡히고, 투자 이체가 지출로 잡히고, 페이 충전이 이중 계산되는 것을 확인했다.
- 뱅크샐러드 내보내기는 최근 1년 치만 준다. 그보다 오래된 기록은 우리가 쌓아 두지 않으면 사라진다.

데이터 경로가 엑셀 내보내기인 이유: 개인이 무료로 쓸 수 있는 경로 중 유일하게 확실하다. 마이데이터·오픈뱅킹 API는 사업자 전용이고, 조회 대행 API는 월 10만원 이상이며, 결제 알림 수집이나 금융 사이트 자동 접속은 누락되거나 깨진다.

## 2. 목표, 비목표, 반목표

### 목표

1. 뱅크샐러드 내보내기 파일의 모든 데이터를 빠짐없이 저장하고 화면 어딘가에서 볼 수 있다(§5의 대응표).
2. 파일을 어떤 주기로, 어떤 순서로 올려도 기존 데이터와 올바르게 합쳐진다. 1년 넘는 기록이 계속 쌓인다.
3. "이번 달 얼마 썼나"가 믿을 수 있는 숫자다. 이체·충전·카드대금·투자를 소비와 구분한다.
4. 월 고정비를 자동으로 찾아 목록과 합계로 보여준다.
5. 지출 패턴(분류별, 가맹점별, 요일·시간대별, 결제수단별, 평소 대비)을 보여준다.
6. 자산·투자·신용점수는 올릴 때마다 한 점씩 쌓여 추이가 된다.
7. 화면은 토스의 디자인 문법을 따르고 PC 화면에 맞게 다듬는다.
8. AI(Claude 등)가 같은 데이터를 읽어 분류 규칙을 제안하고 해석 메모를 남길 수 있다. 사이트는 AI 없이도 완전히 동작한다.
9. 파일의 금액은 믿되 그 밖의 정리는 틀리거나 애매할 수 있다고 본다. 금액과 원본을 제외한 모든 정리(흐름, 분류, 가맹점 이름, 결제수단, 날짜·시간, 메모, 자산의 이름·종류)를 사이트에서 고칠 수 있고, 고친 내용은 저장되어 파일을 새로 올려도 유지된다. 사용자가 직접 요청한 목표다.

### 비목표 (이번에 하지 않는 것)

- 폰이나 집 밖에서의 접속, 로그인, 여러 사용자
- 은행·카드사 직접 연결, 자동 수집, 알림 수집
- 뱅크샐러드 외의 파일 형식(카드사 엑셀 등)
- 예산 설정, 목표 저축, 알림
- 다크 모드
- 시세 조회 등 외부 데이터를 쓰는 투자 분석
- 달력 월이 아닌 월 기준(급여일 기준 등)
- 한 거래를 여러 분류로 쪼개기
- 파일에 없는 거래를 직접 추가하기
- 금액 고치기

### 반목표 (기술적으로 되더라도 실패로 보는 것)

- 금융 데이터가 PC 밖으로 나가는 것: 외부 요청, 원격 폰트·스크립트, git 커밋.
- 조용히 틀린 숫자: 누락이나 이중 계산을 경고 없이 합계에 넣는 것.
- 원본 손실: 가져오기가 과거 기록을 지워 되돌릴 수 없게 되는 것.
- 근거를 알 수 없는 숫자: 화면의 합계가 어떤 거래로 이루어졌는지 따라갈 수 없는 것.

## 3. 제약

- 실행 환경: Windows 11, Node.js 22, 브라우저. 사용자 한 명.
- 비용: 무료. 유료 서비스나 API 키를 전제로 하지 않는다.
- 저장소에는 실제 데이터가 절대 들어가지 않는다. 테스트는 가짜 데이터로 한다.
- 저장소는 현재 비어 있다(커밋 없음).

## 4. 접근 방식

검토한 세 가지:

| 방식 | 내용 | 장단점 |
|---|---|---|
| A. PC에서 도는 사이트 | 로컬 서버와 브라우저 화면. 데이터는 PC의 파일 DB에 저장 | 기록이 디스크에 안전하게 쌓이고, 데이터가 PC 밖으로 안 나가고, AI가 같은 DB를 읽을 수 있다. 집 밖에서는 못 본다 |
| B. 서버 없는 웹페이지 | 브라우저 저장소에 저장 | 폰에서도 열린다. 브라우저 데이터가 지워지면 1년 넘은 기록이 사라지고 AI가 데이터를 읽지 못한다 |
| C. 매번 AI에게 파일 전달 | AI가 그때마다 리포트 생성 | 유연하다. 매번 세션이 필요하고 숫자가 실행마다 달라질 수 있다 |

사용자가 A를 골랐다. 폰으로 볼 필요가 없고, 기록의 안전한 누적과 AI 연결이 중요하기 때문이다.

## 5. 입력: 뱅크샐러드 내보내기 파일

실제 파일(거래 약 1천 행)로 확인한 구조다. 파서는 셀 좌표가 아니라 제목 글자로 구역을 찾는다. 셀 단위의 정확한 배치는 부록 A에 있다.

실제 파일은 사용자 PC에만 있다. 구현 중 구조 확인과 최종 확인에 로컬에서 읽을 수 있지만, 데이터 폴더 밖의 저장소 경로로 복사하지 않고 값을 문서·테스트·로그에 옮기지 않는다.

- 파일명: `YYYY-MM-DD~YYYY-MM-DD.xlsx` (시작일~종료일, 약 1년)
- 암호: 확인한 파일은 암호가 없었다. 암호가 걸린 파일을 만나면 무엇이 문제인지 알려 주고 가져오지 않는다.
- 시트 두 개: `뱅샐현황`, `가계부 내역`

### 시트 `가계부 내역`

첫 행이 제목이고 이후가 거래다. 최신 거래가 위에 온다.

| 열 | 내용 |
|---|---|
| 날짜 | 엑셀 날짜 일련번호 |
| 시간 | 하루 중 비율(초 단위 정밀도). 0은 시간 정보 없음 |
| 타입 | `지출`, `수입`, `이체` |
| 대분류 | 뱅크샐러드 분류(약 30종) |
| 소분류 | 뱅크샐러드 세부 분류(약 50종). 절반 이상이 `미분류` |
| 내용 | 가맹점명 또는 거래 상대 |
| 금액 | 부호 있는 정수. 나간 돈이 음수 |
| 화폐 | 확인한 파일은 전부 `KRW` |
| 결제수단 | 계좌, 카드, 간편결제, 머니, 현금 이름 |
| 메모 | 확인한 파일은 전부 비어 있음 |

확인한 성질:

- 거래 고유번호가 없다.
- (날짜, 시간, 금액, 내용, 결제수단) 조합은 확인한 파일에서 한 건도 겹치지 않았다.
- `지출`인데 금액이 양수인 행이 있다. 취소나 환불이다. 택시처럼 선승인 후 취소가 잦은 가맹점에 많다.
- 금액이 0인 행이 있다.

### 시트 `뱅샐현황`

B열부터 시작하는 보고서 형태다. 구역 제목과 열 제목으로 위치를 찾는다.

| 구역 제목 | 내용 |
|---|---|
| `1.고객정보` | 이름, 성별, 연령(만 나이), 신용점수(KCB), 이메일 |
| `2.현금흐름현황` | 항목 × 월(13개월) 표. 수입 항목들, `월수입 총계`, 지출 항목들, `월지출 총계`, `순수입 총계` |
| `3.재무현황` | 왼쪽에 자산(항목, 상품명, 금액), 오른쪽에 부채(항목, 상품명, 금액). `총자산`, `총부채`, `순자산` |
| `4.보험현황` | 금융사, 보험명, 계약상태, 총납입금, 계약일자, 만기일자 |
| `5.투자현황` | 투자상품종류, 금융사, 상품명, 투자원금, 평가금액, 수익률, 가입일자, 만기일자 |
| `6.대출현황` | 대출종류, 금융사, 상품명, 대출원금, 대출잔액, 대출금리, 대출신규일, 대출만기일 |

확인한 성질:

- 합계 칸은 전부 수식이고 저장된 값이 0이다. 합계는 우리가 직접 계산한다.
- 자산의 `항목` 칸은 세로로 병합돼 있어 첫 행에만 값이 있다. 상품이 없는 항목은 항목명만 있는 빈 행이다.
- 같은 이름의 상품이 여러 개 있을 수 있다.
- 자산 금액에는 소수가 있을 수 있다.
- 수입과 지출 양쪽에 `미분류` 항목이 있다. 구역 경계(`월수입 총계`)로 구분한다.
- 보험과 대출은 확인한 파일에서 비어 있었다. 구조는 지원한다.
- 현금흐름표의 각 칸은 `가계부 내역`에서 같은 타입·대분류·월의 금액 합계의 절댓값과 전부 일치했다. 이 대조를 가져오기 점검에 쓴다.

### 데이터 사용 대응표

| 데이터 | 쓰이는 곳 |
|---|---|
| 거래의 날짜·시간 | 월별·일별·요일별·시간대별 분석, 고정비 주기 |
| 타입·대분류·소분류 | 원본 분류로 보존. 흐름 구분과 분류 분석의 출발점 |
| 내용 | 가맹점 분석, 고정비 탐지, 규칙 조건 |
| 금액 | 모든 합계 |
| 화폐 | 저장하고 내역에 표시. 원화가 아니면 합계에서 빼고 알린다 |
| 결제수단 | 결제수단별 분석, 카드대금 대조 |
| 메모 | 내역에 표시, 검색 |
| 고객정보 | 신용점수 추이. 이름은 내 계좌 간 이동 판별에 쓴다 |
| 현금흐름현황 | 원본 그대로 보기, 가져오기 대조 |
| 재무현황 | 순자산 추이, 자산 구성, 부채 |
| 보험·투자·대출현황 | 자산 화면의 각 구획 |

구역을 못 알아본 셀도 버리지 않는다. `뱅샐현황` 시트 전체의 셀 값을 가져오기마다 원본 그대로 저장한다.

## 6. 가져오기와 업데이트

### 원칙

원장(현재 보이는 거래 목록)은 "지금까지 가져온 파일들의 집합"만으로 결정된다. 가져온 순서나 횟수와 무관하게 같은 결과가 나온다.

### 규칙

- 각 파일은 창(시작일~종료일)을 가진다. 파일명에서 읽고, 거래 날짜가 그 밖에 있으면 창을 넓힌다. 파일명을 읽을 수 없으면 거래 날짜의 최소·최대를 쓴다.
- 파일의 기준일은 창의 종료일이다. 기준일이 같으면 나중에 가져온 파일이 우선한다.
- 원장은 날짜마다, 그 날짜를 창에 포함하는 파일 중 기준일이 가장 늦은 파일의 거래로 채운다.
- 가져온 파일의 모든 행은 파일별로 그대로 보관한다. 원본 파일도 데이터 폴더에 복사해 둔다.
- 같은 파일(내용 해시 동일)을 다시 올리면 "이미 가져온 파일"로 알리고 아무것도 바꾸지 않는다.
- 어떤 가져오기든 되돌릴 수 있다. 되돌리면 남은 파일들로 원장을 다시 계산한다.

이 규칙의 결과:

- 겹치는 기간은 새 파일 기준으로 바뀐다. 뱅크샐러드에서 분류를 고쳤거나, 승인이 취소됐거나, 늦게 들어온 거래가 모두 반영된다.
- 새 파일의 창보다 오래된 기간은 그대로 남는다.
- 옛 파일을 나중에 올려도 새 파일이 덮는 기간은 바뀌지 않는다.

### 결제수단이 통째로 사라진 경우

뱅크샐러드에서 자산 연동을 끊으면 그 자산의 과거 거래가 내보내기에서 빠질 수 있다. 실제로 그런지는 확인하지 못했다. 날짜 규칙만 쓰면 겹치는 기간에서 그 결제수단의 기록이 원장에서 사라지므로 보호 규칙을 둔다. 이 규칙도 파일 집합만으로 결정된다.

- 어떤 날짜의 거래를 정할 때, 그 날짜를 창에 포함하는 더 새로운 파일들의 거래 전체에 한 번도 나오지 않는 결제수단의 거래는 버리지 않는다. 그 결제수단이 나오는 파일 중 가장 새 파일의 거래를 유지한다.
- 단, 더 새로운 파일에 날짜·시간·금액·내용이 같은 거래가 있으면 유지하지 않는다. 결제수단의 이름만 바뀐 경우이기 때문이다. 이때 그 거래에 달린 개별 수정은 새 거래로 옮긴다.
- 결제수단이 새 파일에 다시 나타나면 그때부터는 새 파일이 그 결제수단의 기준이 된다.

### 거래의 지문

사용자의 수정과 가져오기 간 비교를 위해 거래마다 지문을 만든다.

- 지문 = (날짜, 시간, 금액, 내용, 결제수단) + 같은 조합이 같은 날 여러 번 나오면 순번.
- 타입·분류·메모는 지문에 넣지 않는다. 뱅크샐러드에서 분류만 바꾼 거래를 같은 거래로 알아보기 위해서다.
- 원장의 정확성은 지문에 의존하지 않는다. 지문은 개별 수정의 연결과 추가·변경·사라짐 집계에만 쓴다.
- 지문이 내보내기 사이에서 그대로 유지되는지는 파일 하나로만 확인했다. 같은 거래의 시간이나 표기가 내보낼 때마다 달라질 가능성이 남아 있다. 그래서 다음을 지킨다.
  - 지문은 보관된 원본 행에서 언제든 다시 계산할 수 있어야 한다. 정의를 바꿀 수 있게 만든다.
  - 수정이 연결된 거래가 사라지면 느슨한 대조(같은 날짜와 금액, 내용이나 결제수단 중 하나가 같고 후보가 하나뿐)로 다시 연결할 거래를 찾아 제안한다.
  - 겹치는 기간에서 사라짐과 추가가 한꺼번에 많이 나오면 미리보기에서 "파일의 표기가 달라진 것 같다"고 알린다.
  - 두 번째 실제 파일을 올릴 때 지문이 유지되는지 확인한다.

### 미리보기와 적용

파일을 올리면 바로 적용하지 않고 미리보기를 먼저 보여준다.

- 기간, 거래 수
- 원장 대비 추가, 변경(지문은 같고 타입·분류·메모가 다름), 사라짐 건수
- 현금흐름표 대조 결과(§5)
- 새 파일에 없는 결제수단과 그 때문에 유지되는 거래 수, 이름이 바뀐 것으로 보이는 결제수단
- 결제수단은 남아 있는데 오래된 기간의 거래가 사라진 경우는 결제수단별로 묶어 따로 표시한다.

사용자가 적용을 누르면 반영한다. 적용 직전에 DB 백업을 남긴다.

### 스냅샷 데이터

`뱅샐현황`의 고객정보·자산·부채·보험·투자·대출·현금흐름표는 파일의 기준일에 딸린 스냅샷으로 저장한다. 추이 그래프는 기준일별 스냅샷을 점으로 쓴다. 같은 기준일의 스냅샷이 둘이면 나중에 가져온 것을 쓴다.

### 구조가 바뀐 파일

필수 시트나 열 제목이 없으면 무엇이 없는지 알려 주고 아무것도 가져오지 않는다. 일부만 가져오는 일은 없다. 모르는 열이나 구역이 추가된 경우는 가져오되 미리보기에 알린다.

## 7. 분류 보정

뱅크샐러드의 원본 값은 절대 바꾸지 않는다. 그 위에 세 층을 얹어 "유효 분류"를 만든다. 우선순위는 개별 수정, 내 규칙, 기본 규칙 순이다.

### 흐름 구분

거래마다 흐름을 하나 정한다. 소비 분석은 `소비`만 센다.

| 흐름 | 뜻 |
|---|---|
| 소비 | 실제로 쓴 돈. 환불(양수 금액)은 차감한다 |
| 수입 | 급여, 이자, 기타 번 돈 |
| 저축·투자 | 예적금, 증권, MMF 등으로 옮긴 돈 |
| 내 계좌 간 이동 | 내 계좌·머니·현금 사이의 이동, 페이 충전 |
| 카드대금 | 계좌에서 카드사로 나간 결제대금 |
| 송금·입금 | 다른 사람이나 알 수 없는 상대와 주고받은 돈 |

### 기본 규칙

데이터로 저장하고 화면에서 켜고 끌 수 있다. 위에서부터 먼저 맞는 것을 적용한다. 실제 파일에서 본 왜곡을 바로잡는 출발점이며, 세부 조정은 빌더 재량이다.

1. 내용에 `급여`가 있고 금액이 양수면 수입(급여).
2. 소분류가 `결제/충전`이거나 내용이 충전을 뜻하면 내 계좌 간 이동.
3. 타입이 `이체`이고 내용이 고객정보의 이름과 같거나 가운데가 가려진 형태(예: 첫 글자 + `*` + 끝 글자)면 내 계좌 간 이동.
4. 대분류가 `카드대금`이거나 대분류 `금융`·소분류 `카드`인 거래 중, 내용에 `카드`가 있고 결제수단이 계좌면 카드대금.
5. 대분류 `금융`·소분류 `증권/투자`면 저축·투자.
6. 대분류 `금융`·소분류 `은행`이면 송금·입금.
7. 타입 `이체`·대분류 `내계좌이체`면 내 계좌 간 이동.
8. 타입 `이체`·대분류 `투자`면 저축·투자.
9. 그 밖의 타입 `이체`는 송금·입금.
10. 타입 `지출`은 소비, 타입 `수입`은 수입.

뱅크샐러드의 `카드대금`과 `저축` 대분류는 믿을 수 없다. 사람에게 보낸 송금이 `카드대금`으로, 계좌로 들어온 돈이 `저축`으로 잡힌 것을 확인했다. 그래서 4번은 내용에 `카드`가 있을 때만 적용하고, `저축`은 따로 규칙을 두지 않는다.

### 내 규칙과 개별 수정

- 개별 수정: 거래 하나의 흐름·대분류·소분류·메모를 고친다. 지문에 연결돼 파일을 새로 올려도 유지된다.
- 내 규칙: 조건(내용 포함·일치, 결제수단, 금액 부호·범위, 원본 분류)에 맞는 모든 거래에 흐름과 분류를 지정한다. 내역 화면에서 "이 가맹점은 항상 이렇게"로 바로 만들 수 있다.
- 수정이 연결된 거래가 원장에서 사라지면 수정은 지우지 않고 관리 화면에 "연결이 끊긴 수정"으로 보여준다.

기본값으로 정한 것: 다른 사람에게 보낸 송금은 소비로 세지 않는다. 월세처럼 소비인 송금은 규칙으로 바꾼다.

### 분류 바꾸기

사용자가 직접 요청한 기능이다. 뱅크샐러드가 가맹점을 엉뚱하게 분류한 경우를 바로잡는다. 예: 미용실이 `카페/간식`·`베이커리`로 잡혀 있어 `뷰티/미용`·`헤어샵`으로 옮긴다.

- 어디서: 내역의 거래 상세, 소비 화면의 가맹점 목록.
- 무엇을: 대분류와 소분류. 기존 분류 중에서 고르거나 새 이름을 입력해 만든다.
- 범위: "이 거래만"(개별 수정) 또는 "이 가맹점 전체"(내용이 같은 과거 거래와 앞으로 들어올 거래 모두. 내 규칙으로 저장). 기본 선택은 "이 가맹점 전체"다. 적용 전에 바뀌는 거래 수를 보여준다.
- 결과: 소비 분석, 고정비 탐지, 홈의 숫자가 모두 바뀐 분류를 따른다. 원본 분류는 거래 상세에 남고, 바뀐 거래에는 작은 표시가 붙는다.
- 되돌리기: 규칙이나 수정을 지우면 원본 분류로 돌아간다.
- 분류 이름을 한꺼번에 바꾸거나 합치는 분류 목록 관리는 이번 범위가 아니다.

### 보정 범위

사용자가 직접 요청했다. 금액은 정확하다고 보고 고치지 않는다. 그 밖의 것은 전부 사이트에서 고칠 수 있다.

| 대상 | 고칠 수 있는 것 | 단위 |
|---|---|---|
| 거래 | 흐름, 대분류, 소분류, 메모, 날짜·시간, 결제수단, 분석에서 제외 | 한 건, 또는 여러 건을 골라 한 번에 |
| 가맹점(내용) | 표시 이름, 여러 표기를 한 가맹점으로 합치기, 흐름·분류 | 가맹점 전체(규칙) |
| 결제수단 | 표시 이름, 종류, 카드사 | 결제수단 전체 |
| 자산·부채·투자 상품 | 표시 이름, 종류(항목), 순자산에서 제외 | 상품 하나 |
| 고정비 | 확정·제외, 이름, 직접 추가 | 가맹점 |

고칠 수 없는 것: 금액, 화폐, 원본 값 자체.

원칙:

- 원본은 바꾸지 않는다. 보정은 원본 위에 덧씌우는 별도 기록이다.
- 보정은 모두 DB에 저장된다. 파일을 새로 올려도, 가져오기를 되돌려도 유지된다.
- 보정된 값에는 표시가 붙고 원본 값을 언제든 볼 수 있다.
- 보정은 하나씩 되돌릴 수 있다. 관리 화면의 "보정 내역"에서 고친 것 전부를 본다.
- 날짜·시간과 결제수단은 개별 거래에서만 고친다. 분석은 고친 값을 따르고, 가져오기 규칙(§6)과 지문은 원본 값을 쓴다.
- 가맹점에 표시 이름을 주면 화면과 분석이 그 이름을 쓴다. 여러 표기에 같은 표시 이름을 주면 한 가맹점으로 합쳐진다. 고정비 탐지도 합친 뒤의 이름으로 한다.
- "분석에서 제외"한 거래는 모든 합계에서 빠진다. 내역에는 표시와 함께 남는다. 중복된 기록에 쓴다.
- 자산·부채·투자 상품의 보정은 (원본 항목, 원본 상품명, 같은 이름 안에서의 순번)에 연결한다. 이름이 같은 상품이 여러 개면 순번이 뒤바뀔 수 있다는 한계가 있다.

### 검토 대기열

애매한 것을 사용자가 찾아다니지 않도록 사이트가 모아서 보여준다.

- 소비인데 소분류가 `미분류`인 거래
- 같은 가맹점인데 분류가 서로 다르게 섞여 있는 경우
- 흐름이 송금·입금인 큰 금액
- 중복 의심(§8)
- AI가 제안한 규칙

항목마다 고치거나 "이대로 맞음"으로 확인한다. 확인한 것은 다시 나오지 않는다. 가맹점 단위로 묶어 한 번에 처리할 수 있다.

## 8. 결제수단과 데이터 점검

### 결제수단 관리

파일에 나온 결제수단마다 표시 이름, 종류(계좌, 신용카드, 체크카드, 간편결제, 머니·포인트, 현금), 카드사를 지정한다. 종류와 카드사는 이름으로 추정해 채워 두고 사용자가 고친다. `저축예금`처럼 뜻을 알기 어려운 이름은 표시 이름으로 바꿔 쓴다.

### 데이터 점검

숫자를 왜곡할 수 있는 상태를 찾아 관리 화면과 홈에 알린다. 자동으로 합계를 바꾸지는 않는다.

- 사용 내역이 없는 카드: 카드대금은 나가는데 그 카드사에 지정된 결제수단이 없는 경우. 뱅크샐러드에 카드가 연동되지 않았을 가능성이 높다. 사용자는 "뱅크샐러드에 연동하겠다", "이 대금을 소비로 계산", "무시" 중 하나를 고른다. 기본은 소비에 넣지 않고 경고만 한다. 잘못 넣으면 이중 계산이 되기 때문이다.
- 중복 의심: 같은 날 비슷한 시각에 같은 금액이 간편결제와 카드 양쪽에 있는 경우.
- 빈 기간: 어떤 파일의 창에도 들지 않는 날짜 구간.
- 현금흐름표 대조 불일치.
- 연결이 끊긴 수정.
- 흐름이 송금·입금인 큰 금액 중 아직 확인하지 않은 것.

## 9. 고정비

원장에서 정기적으로 반복되는 나가는 돈을 찾는다. 대상은 소비뿐 아니라 송금과 저축·투자도 포함한다. 월세나 적금 자동이체가 이체로 잡히기 때문이다.

- 탐지: 같은 가맹점(내용을 정규화해 비교)이 세 번 이상, 대략 한 달 간격으로 나타나면 후보다. 금액이 거의 같으면 고정 금액, 달라지면 변동 금액(통신비 등)으로 표시한다. 소분류(`서비스구독`, `휴대폰`, `보험`, `인터넷` 등)를 힌트로 쓴다.
- 상태: 최근에도 결제됐으면 진행 중, 한동안 없으면 종료 추정.
- 사용자 확정: 후보를 확정하거나 제외한다. 직접 추가도 된다. 결정은 가맹점 기준으로 저장돼 파일을 새로 올려도 유지된다.
- 구분: 흐름이 저축·투자인 것은 "정기 저축"으로 따로 보여주고 고정비 합계에 넣지 않는다.
- 연 단위 반복(연회비 등)은 자동 탐지하지 않는다. 직접 추가로 처리한다.
- 세부 기준(간격·금액 허용 범위, 정규화 방법)은 빌더 재량이다.

데이터가 없을 때는 뱅크샐러드에서 내보내는 방법과 파일을 끌어다 놓는 자리를 보여준다. 파일은 어느 화면에서든 끌어다 놓을 수 있다.

### 소비

- 월 선택, 월 합계, 지난달과 최근 평균 대비
- 대분류 → 소분류 → 가맹점으로 내려가는 구성
- 가맹점 순위(금액, 횟수). 여기서 바로 가맹점의 분류를 바꿀 수 있다
- 일별 달력, 요일별, 시간대별
- 결제수단별
- 큰 지출, 평소보다 많이 쓴 분류
- 취소·환불 목록

### 고정비

- 월 고정비 합계와 항목 목록(이름, 주기, 최근 금액, 다음 예상일, 결제수단)
- 확정 대기 후보, 종료 추정, 정기 저축
- 금액이 오른 항목 표시

### 수입·흐름

- 월별 수입, 소비, 저축·투자, 송금·입금, 순흐름
- 수입원별 구성
- 뱅크샐러드 원본 현금흐름표 그대로 보기와 대조 결과

### 자산

- 순자산 추이(가져온 기준일마다 한 점), 자산 구성(항목 → 상품), 부채
- 투자(원금, 평가금액, 손익, 수익률), 보험, 대출
- 신용점수 추이
- 상품마다 표시 이름과 종류를 바꾸거나 순자산에서 제외할 수 있다
- 스냅샷이 하나뿐이면 추이 자리에 현재 값과 "다음 업데이트부터 추이가 그려져요" 안내

### 내역

- 전체 거래 목록. 검색과 필터(기간, 흐름, 원본 타입·분류, 결제수단, 금액 범위, 메모, 수정 여부, 확인 필요, 분석 제외, 0원 포함)
- 거래 상세: 원본 열 10개 전부, 유효 값, 적용된 규칙, 수정(§7의 보정 범위 전부), "이 가맹점은 항상 이렇게"
- 여러 건을 골라 흐름·분류를 한 번에 바꾸기

### 관리

- 업데이트 기록: 가져온 파일 목록, 가져오기별 추가·변경·사라짐, 되돌리기
- 규칙: 기본 규칙 켜고 끄기, 내 규칙, AI가 제안한 규칙의 수락·거절
- 결제수단: 종류와 카드사 지정
- 데이터 점검: §8의 목록
- 검토 대기열: §7의 목록. 홈의 "확인이 필요해요"에서도 들어온다
- 보정 내역: 내가 고친 것 전부(개별 수정, 규칙, 표시 이름, 제외). 하나씩 되돌리기

## 11. 디자인

토스의 디자인 문법을 따른다.

- 옅은 회색 바탕 위에 흰 카드, 큰 모서리 반경, 넉넉한 여백
- 화면마다 가장 중요한 숫자 하나를 크게. 숫자는 폭이 고정된 글꼴 설정
- 강조색은 파랑 하나. 회색 계조로 위계를 만들고, 빨강은 초과·경고에만
- 짧은 해요체 문장("지난달보다 00만원 덜 썼어요")
- 차트는 축과 격자를 최소로

토스의 로고, 이름, 전용 서체는 쓰지 않는다. 서체는 공개 서체인 Pretendard를 저장소에 포함해 쓴다.

토스에서 더 다듬는 점(내 제안):

- PC 폭을 쓰는 여러 단 구성. 토스는 폰 한 단 기준이다.
- 모든 숫자에서 근거 거래로 이어지는 연결
- 금액 숨기기 전환(화면을 남에게 보일 때)
- 보정된 값에는 작은 표시를 붙여 원본과 다름을 알린다

밝은 테마만 만든다. 색 대비와 키보드 초점 표시는 지킨다. 세부 색상 값, 간격, 구성 요소 설계는 빌더 재량이다.

## 12. AI 연결

원칙: 숫자는 코드가 계산하고 AI는 제안하고 해석한다.

- 사이트는 AI를 호출하지 않는다. 사용자가 이 프로젝트 폴더에서 Claude Code(또는 다른 코딩 에이전트)를 불러 요청한다. 구독만으로 되고 API 키가 필요 없다.
- AI가 쓰는 통로는 명령줄 도구다. 필요한 기능:
  - 분석 요약 읽기: 월별·분류별 합계, 가맹점 순위, 고정비 후보, 분류가 애매한 거래 묶음, 데이터 점검 결과
  - 규칙 제안 쓰기: "제안" 상태로 저장되고 사용자가 관리 화면에서 수락해야 적용된다
  - 해석 메모 쓰기: 홈의 "AI 메모"와 목록에 표시된다. 관련 거래 필터로 가는 연결을 달 수 있다
- 프로젝트에 AI용 안내(절차와 안전 규칙)와 호출 명령을 둔다.
- AI가 쓴 내용은 항상 AI가 썼다고 표시한다.
- AI를 부르면 도구가 출력한 내용이 그 AI 회사 서버를 거친다. 사이트만 쓸 때는 아무것도 나가지 않는다.

AI에게 보여주는 범위(사용자가 정했다):

- 모든 거래를 개별 단위(날짜, 금액, 내용, 분류, 결제수단, 메모)로 그대로 보여준다. 송금 상대의 이름과 본인 이름도 가명으로 바꾸지 않는다.
- 자산·투자·신용점수도 보여준다. 고객정보의 이메일은 분석에 쓸 데가 없어 넣지 않는다.
- AI용 안내에 "데이터 폴더의 DB와 원본 파일을 직접 읽지 말고 도구를 쓸 것"을 적는다. 숫자를 화면과 같은 계산으로 받게 하기 위해서다. 기술적으로 막지는 않는다.

명령줄 도구의 정확한 모양은 빌더 재량이다.

## 13. 기술 선택

사용자가 맡긴 부분이라 내가 정했다.

- 언어: TypeScript 하나로 서버와 화면을 모두 만든다.
- 서버: Node.js 22의 작은 HTTP 서버. `127.0.0.1`에만 연다.
- 저장: SQLite 파일 하나.
- 화면: React와 Vite.
- 실행: 명령 하나로 서버가 뜨고 브라우저가 열린다. Windows에서 두 번 눌러 실행하는 파일도 둔다.
- 엑셀 읽기: xlsx는 zip 안의 XML이라 직접 읽거나 라이브러리를 쓴다.
- 테스트: Vitest.

서버 프레임워크, SQLite 드라이버, 스타일 방식, 차트 구현, 엑셀 라이브러리 선택은 빌더 재량이다. 조건은 실행 중 외부 네트워크 요청이 없을 것과 Windows에서 설치가 쉬울 것이다.

## 14. 개인정보와 안전

- 서버는 `127.0.0.1`에만 연다.
- 데이터 폴더(DB, 원본 파일 사본, 백업)는 저장소 안의 한 폴더에 두고 `.gitignore`로 막는다. 이것이 첫 작업이다.
- 화면은 외부 자원을 불러오지 않는다. 서체와 스크립트는 전부 로컬이다.
- 테스트 자료는 가짜 데이터로 만든 파일만 쓴다. 실제 파일과 같은 구조의 엑셀을 만드는 생성기를 둔다.
- 로그에 거래 내용을 남기지 않는다.

## 15. 검증

반드시 통과해야 하는 경우:

1. 같은 파일을 다시 올리면 아무것도 바뀌지 않는다.
2. 창이 겹치는 두 파일: 겹치는 기간은 새 파일 기준, 그 이전은 유지.
3. 두 파일을 반대 순서로 올려도 원장이 같다.
4. 가져오기를 되돌리면 원장이 그 전 상태가 된다.
5. 뱅크샐러드에서 분류만 바뀐 거래는 "변경"으로 세고, 개별 수정은 유지된다.
6. 새 파일에서 없어진 거래가 "사라짐"으로 보고된다.
7. 지문이 같은 거래 두 건이 둘 다 보존된다.
8. 현금흐름표 대조가 일치와 불일치를 올바로 가린다.
9. 양수 금액의 지출이 소비 합계에서 차감된다.
10. 기본 규칙 각각이 의도한 흐름을 만든다.
11. 고정비 탐지가 월 주기, 금액 변동, 종료를 구분한다.
12. 필수 열이 빠진 파일은 가져오지 않고 무엇이 빠졌는지 알린다.
13. 실행 중 외부 네트워크 요청이 없다.
14. 새 파일에 통째로 없는 결제수단의 겹치는 기간 거래가 유지된다.
15. 결제수단 이름만 바뀐 경우 거래가 중복되지 않고 개별 수정이 새 거래로 옮겨진다.
16. 연결이 끊긴 수정에 대해 느슨한 대조가 후보를 제안한다.
17. AI용 도구의 출력에 거래의 내용과 이름이 원본 그대로 나오고, 합계가 화면의 합계와 같다.
18. 가맹점 전체의 분류를 바꾸면 과거 거래와 이후에 가져온 거래에 모두 적용되고, 규칙을 지우면 원본 분류로 돌아간다.
19. §7의 모든 보정이 새 파일을 가져온 뒤에도, 가져오기를 되돌린 뒤에도 유지된다.
20. 여러 표기에 같은 표시 이름을 주면 분석에서 한 가맹점으로 집계된다.
21. 분석에서 제외한 거래가 모든 합계에서 빠지고 내역에는 남는다.
22. 날짜를 고친 거래는 고친 월에 집계되고, 가져오기 비교는 원본 날짜로 한다.
23. 검토 대기열에서 확인한 항목이 다시 나오지 않는다.
24. 어떤 보정으로도 금액과 원본 값이 바뀌지 않는다.

구조 진단 명령을 둔다. 실제 파일의 구조(시트, 구역 제목, 열 제목, 행 수, 셀 형식)만 출력하고 값은 출력하지 않는다. 뱅크샐러드가 형식을 바꿨을 때 원인을 찾는 데 쓴다.

실제 파일 확인(사용자 PC에서만): 모든 행이 가져와지고 현금흐름표 대조가 전부 일치한다.

## 부록 A. 파일의 셀 배치

실제 파일에서 본 배치다. 값은 적지 않았다. 행 번호는 항목 수에 따라 밀리므로 예시로만 본다. 파서는 제목 글자로 찾는다.

### `가계부 내역`

- A~J열. 1행이 제목: `날짜`, `시간`, `타입`, `대분류`, `소분류`, `내용`, `금액`, `화폐`, `결제수단`, `메모`
- `날짜`: 숫자(엑셀 날짜 일련번호), 표시 형식 `yyyy-mm-dd`
- `시간`: 숫자(하루 중 비율), 표시 형식 `hh:mm`. 초 단위까지 들어 있다
- `금액`: 숫자. 나머지는 글자
- 빈 메모는 셀 자체가 없다

### `뱅샐현황`

B열에서 시작한다. 각 구역은 제목 행, 설명 문장 행, 열 제목 행, 데이터 행 순이다.

**`1.고객정보`** (가로 배치)

- 열 제목 행: B `이름`, C `성별`, D `연령` + 줄바꿈 + `(만 나이)`, E `신용점수` + 줄바꿈 + `(KCB)`, F `이메일`(F:G 병합)
- 바로 아래 행이 값. 연령과 신용점수는 숫자. 이메일이 없으면 `-`

**`2.현금흐름현황`**

- 열 제목 행: B `항목`, C `총계`, D `월평균`, E부터 월 13개. 월은 `YYYY-MM` 형식의 글자
- 수입 항목 행들, `월수입 총계`, 지출 항목 행들, `월지출 총계`, `순수입 총계` 순
- 항목 행의 월별 칸은 숫자(양수). `총계`·`월평균` 열과 세 총계 행은 수식(저장된 값 0)
- 항목 목록은 데이터에 따라 달라진다고 본다

**`3.재무현황`**

- 한 행에 B `자산`(B:E 병합), F `부채`(F:I 병합)
- 열 제목 행: B `항목`, C `상품명`(C:D 병합), E `금액`, F `항목`, G `상품명`(G:H 병합), I `금액`
- 데이터 행: 자산은 B(항목, 세로 병합), C(상품명), E(금액). 부채는 F(항목), G(상품명), I(금액)
- 자산 항목 예: `자유입출금 자산`, `신탁 자산`, `현금 자산`, `저축성 자산`, `전자금융 자산`, `투자성 자산`, `부동산`, `동산`, `기타 실물 자산`, `보험 자산`, `연금 자산`. 부채 항목 예: `장기대출`
- 끝 행: B `총자산`(B:D 병합)과 E의 수식, F `총부채`(F:H 병합)와 I의 수식
- 그 아래 B `순자산`(B:I 병합), 다음 행 B에 수식

**`4.보험현황`**

- 열 제목 행: B `금융사`, C `보험명`(C:D 병합), E `계약상태`, F `총납입금`, G `계약일자`, H `만기일자`
- 데이터 행들(확인한 파일은 0행)
- 총계 블록: B `총계`, C `보유계약건수`, E `정상 N건`, F `총 납입금`. 다음 행에 C `총 N건`, E `만기/휴면 N건`, F 수식

**`5.투자현황`**

- 열 제목 행: B `투자상품종류`, C `금융사`, D `상품명`, F `투자원금`, G `평가금액`, H `수익률`, I `가입일자`, J `만기일자`
- `수익률`은 퍼센트 단위 숫자(예: 12.3은 12.3%). `가입일자`·`만기일자`는 엑셀 날짜 일련번호이고 비어 있을 수 있다
- 총계 블록: B `총계`, D `보유상품개수`, F `총 투자 원금`, G `총 평가 금액`, H `총 수익률`. 다음 행에 D `총 N개`, F·G·H 수식

**`6.대출현황`**

- 열 제목 행: B `대출종류`, C `금융사`, D `상품명`, F `대출원금`, G `대출잔액`, H `대출금리`, I `대출신규일`, J `대출만기일`
- 데이터 행들(확인한 파일은 0행)
- 총계 블록: B `총계`, D `보유 대출 상품`, F `총 대출 원금`, G `총 대출 잔액`. 다음 행에 수식
